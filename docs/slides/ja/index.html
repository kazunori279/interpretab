Interpretab · Gemini Live API で動く Chrome 拡張機能
Interpretab · github.com/kazunori279/interpretab
Interpretab という Chrome 拡張機能です。タブが再生している音声をそのまま聞き取って、声に出して通訳します。 マイクなら向きが逆になります。あいだにサーバーはありません。接続も API キーも、ブラウザの中だけで完結します。 まずは見てもらったほうが早いです。
デモ: タブを通訳する
どんなタブでも
動画、ウェビナー、ポッドキャスト。元の言語は指定するのではなく、自動で判別する。
声で出る
通訳を音声で再生する。元の音声は 15% まで下げて、その下に流したまま。
字幕も出る
ページの上に 3 行のロール字幕。サイドパネルには全文が残る。
Interpretab
クリップは自動で流れる。まず字幕の行、次にパネルの全文、最後に中国語へ切り替わるところで言語メニューを指す。
デモ: 自分の声を通訳する
あなたの声
話しはじめた時点で拾い、文が終わる前から訳しはじめる。
双方向
会話の両側が 1 つのパネルに、それぞれ相手の言語で並ぶ。
通話の中へ
Meet がマイクとして一覧に出すので、相手には訳した声が届く。
Interpretab
後半は双方向モード。1 つのパネルに 2 言語で、どちらの向きかは自分で判定している。

アーキテクチャ
Interpretab
全体の形です。知らないかもしれない部品が 3 つあります。Web Audio はブラウザの音声グラフで、 取得とサンプルレート変換をやっています。WebSocket は開いたままの接続で、どちらの端からでも好きなときに 送れます。そして Live API は、音声を入れると文が終わる前に音声を返してきます。これが全部、1 つの offscreen document の中にあります。Service Worker は 30 秒アイドルで止められるし、サイドパネルは 閉じれば死ぬからです。AudioContext は 3 つ、サンプルレートで共有しています。Chrome が 1 ドキュメントに 6 個くらいしかくれないので。
2 つの Live モデル
Interpretab
モデルが 2 つあって、この先ずっと出てきます。タブの音声はいつでもライブ翻訳のほう。話している最中から 訳しはじめて、元の言語は自分で判別して、system instruction は受け取りません。マイクはそれか、会話モデルの どちらか。会話モデルはターンが終わるのを待ちます。遅いぶん正確で、しかも安くて、用語集が届くのはこちらだけです。
Meet とどう組み合わさるか
拡張機能が OS に音声入力を登録することはできない。ページなら話は別。
Interpretab
Meet です。拡張機能が OS にマイクとして登録されることはできません。でもページならできる。 そこで Meet 自身の JavaScript ワールドにスクリプトを注入して、Interpretab という名前のデバイスを 一覧に足します。Meet がマイクを要求すると、合成したトラックが返ります。厄介なのは、ページのスクリプトからは 拡張機能に手が届かないこと。だからもう 1 本のスクリプトが postMessage で音声を運びます。実際の通話で 端から端まで、口から相手の耳までおよそ 3 秒。もとは 4 秒で、そのうち 1 秒は Meet の Studio Sound でした。
手強かったところ
抵抗してきた 3 つ
  • セッションは約 10 分で切れる
  • 失敗は理由なしで届く
  • モデルは preview
Interpretab
さて、本当に抵抗してきたのは 3 つです。どれも翻訳の品質の話ではありません。3 つとも、 他人の都合で動く長い接続を、まっとうに保ちつづける話です。
セッションのライフサイクル
Live API のソケットは約 10 分が上限。ここで驚かれることが多い。サーバーは 9 分で警告し、猶予は 50 秒、そして期限は文字どおり守る。
Interpretab
これはあまり知られていないやつです。Live API のソケットは 10 分くらいしかもちません。9 分で サーバーが goAway を送ってきて、猶予は 50 秒、そして本当に切ります。だからループは、古いソケットがまだ 話しているうちに次を開いて、ターンが終わるか 5 秒の無音で切り替えます。古いほうが答えられなかったぶんは、 新しいほうへ送り直します。1 時間で 6 回の引き継ぎ、訳した声が途切れた最悪の間隔は 3 秒 6 でした。 API 自身にもこのための仕組みがあります、session resumption です。試しました。トークンを持って繋ぎ直すと、 モデルが最後の 1 文をもう一度、声に出して言い直します。なので自前のバッファのままにしました。
エラーの扱い
WebSocket の upgrade がなぜ拒否されたのか、ブラウザには決して知らされない。しかもそれは意図的なもの。
1006、理由なし
キーの誤り、使い切った quota、キャプティブポータル。どれも同じ閉じかたをする。区別できたら、 ページがクロスオリジンの oracle になってしまう。
なら先に HTTP で訊く
同じキーで GET /v1beta/models を 1 回、キャプチャの許可を求める前に。 400 はキーが拒否された。401 はキーの形として読むことすら断られた。
1011、セッションの途中で
実行の最中に quota を越えると、きれいに閉じたうえで、URL の途中で切れた 123 バイトの 英文を持ってくる。10 回リトライすれば 10 回とも繋がって 10 回とも死ぬ。
どちらの形も、考えて出したものではなく実際の API に当てて出たもの。 tests/quota-close.mjs は無料枠の上限を 100 トークンまで下げるので、1 セッションが 6 秒で越える。答えが変わらないのにリトライしつづけるのはバグ。使い切った quota が戻るのは太平洋時間の 深夜であって、4 秒後ではない。
Interpretab
WebSocket の upgrade が断られたとき、その理由はブラウザには知らされません。キーが違う、 quota を使い切った、ホテルの Wi-Fi。全部おなじ空っぽの close です。しかもこれは意図的で、でないとページが oracle になってしまう。だから同じことを先に HTTP で訊きます。あちらならステータスコードが返ってくる。 それと、判定はリトライしない。使い切った quota が戻るのは深夜であって、4 秒後ではありません。
新しい Live モデルへ自動で移行する
Interpretab
どの Live モデルが存在するかは、このビルドが決めていい話ではありません。preview は 2 週間の 予告で引退するし、ストアの審査はそれより長くかかることもある。モデル名を焼き込むのは、日付の決まった 障害を出荷するようなものです。かわりに、毎時 GitHub Actions が API にまだ答えるかを訊いて、毎日もう 1 本が 後継を探します。本当に消えていたら、スライド下のファイルに新しい名前をコミットします。中身はこれだけ、 名前と価格とリンク。インストール済みのコピーが全部これを取りに来て、次のセッション引き継ぎで、実行の 途中から乗り換えます。誰も更新作業をしません。
